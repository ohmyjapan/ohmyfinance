# Navi receipt candidate lookup

The company conversation can call `find_company_receipt_matches(receiptId)` to compare a saved receipt with OMF's existing transaction suggestions. This fills the gap between reading a receipt and investigating which purchase it supports. It does not save a link.

The tool uses the frozen job's company. The existing worker checks membership and the live lease before and after the read. Arguments contain only the receipt id; the caller cannot supply another company. `getCompanyReceipt` reads the whitelisted receipt/OCR facts and checks any existing link; `findCompanyMatchesForReceipt` filters both the receipt and transactions by company before the native candidate cap. Candidate details come from `getCompanyNaviTransaction`, preserving original card-source currency, accounting references, item text and explicit unknowns without exposing raw metadata, paths or contacts.

The native matcher is unchanged: an amount tolerance and date window when recorded, the newest twenty eligible rows before ranking and at most ten returned suggestions. The result explicitly says the lookup is not exhaustive. `heuristicScore` and `factors` are copied from the native suggestions; a score is neither a probability nor a verified purchase link. Two same-price purchases remain two candidates. Different currencies and an unrecorded currency remain visible. Saved receipt text is OCR evidence, not verification of a tax document or its purchase purpose. Empty suggestions do not prove that no corresponding transaction exists. Navi can use its other record/history/research tools to pursue the uncertainty.

No receipt, transaction, knowledge, posting or classification is changed by this tool. Linking, OCR and deletion still use the receipt page's existing flow. The legacy global matcher, scorer, native receipt APIs, authorization policy and worker lease checks are unchanged. New branches are the named read dispatch and the usual missing-receipt response if a receipt disappears between reads; these require the scoped release review before deployment.

Callers: the company tool catalogue feeds worker MCP discovery; `financeCompanyAssistantService.companyAction` validates the named arguments and dispatches through `businessRead`. The receipts feature advertises the new tool. Owner conversations retain their existing feature dispositions.

`finance-navi-receipt-matches-integration.cjs` runs inside the existing owned company-business fixture against the actual compiled app and disposable MongoDB. It covers native ranking parity, same-price ambiguity, card/different/unknown currencies, foreign/unassigned/crowded candidates, bounds, private field exclusion, company switch, removed membership, stale lease, malformed arguments, concurrency and unchanged domain snapshots. Its worker replies are simulated; they are not evidence of model reasoning quality. The old compiled app fails `receipt-navi:available` with the missing-tool 400 response.
