# Closed Navi status and exact reply read state — 2026-10-23

Goal row G8 (plan `omf-navi-agent-status-20261022`, chosen design `omf-navi-agent-finish-20261022/6-status-state-design.md`). The closed character shows real work status and new replies of the conversation it opens, before any transcript mounts; a reply counts as read only when its live text was actually visible in the open chat. No model decision, financial approval, worker capability or action policy changes.

## Delivered versions (server)

- `turns[].replyVersion` (owner workspace `FinanceAssistant`, company `FinanceCompanyAssistant`, purchase `FinanceChat`): `finishAssistant`, `finishCompanyAssistant` and `finishChat` add `$inc 'turns.$[turn].replyVersion': 1` inside their existing lease-checked result write, only when a readable proposal is saved. A failed result, a lost/wrong lease, a card-only worker, a claim, heartbeat, action receipt, confirmation, retry or archive writes no version.
- `FinanceResearch.reportVersion` (schema field, default 0, no migration): `finishResearch` adds `$inc reportVersion: 1` in its lease-checked write only with a validated report. Queue, failure, apply, supplier and attachment writes keep it. The research view projection (`financeResearchService.ts` `visible`) now also carries `requestId` and `reportVersion`, so the rendered report can be named exactly.
- Legacy rows: a saved reply or report without a version is version 0, "unknown". It is counted as readable (`replies.readable`, `replies.legacyUnknown` while it has no read record) but never as new; only version 1+ arrivals make the new-reply count.
- Read records live on the same live turn: `turns[].seenReplyVersion` and `turns[].seenResearchVersion` (absent = no read record, which differs from a legacy turn seen at 0). No collection, index, token list or browser storage was added.

## Status and read routes (`server/api/finance-chat/[...path].ts` → `server/services/financeNaviStatusService.ts`)

Named continuations under the existing authenticated routes only; no generic realm/actor/company selector and no body authority.

| Realm | Status (GET, pure read) | Acknowledgement (POST) | Authority |
| --- | --- | --- | --- |
| Owner workspace | `/api/finance-chat/workspace/status` | `/api/finance-chat/workspace/read` | token user; `maskTurns` for the posting company `selectedPostingCompany` checks now |
| Company | `/api/finance-chat/company-workspace/status` | `/api/finance-chat/company-workspace/read` | `calendarCompany` (token company + fresh membership) and the service's own `companyMembership` + active organization |
| Purchase line | `/api/finance-chat/imports/:importId/drafts/:line/status` | `.../read` | `readDraftSourceContext` (the draft service's existing read-only `context`: owned import, owned account, existing editable line, source/mapping/saved key-hash match) and the same `maskTurns` |

Status returns `{realm, scope, observedAt, connected, conversation:{id, segment, state, work}|null, replies:{unread, latestUnread, readable, legacyUnknown}, research?, company?}`. No reply, report, question or turn text, no context, no lease token and no deadline. It reads a narrow projection with `findOne`/`exists` only: it never calls `getAssistant`, `getCompanyAssistant`, `getChat`, `researchView` or `readDraft` (no confirmation, deferred-research, applying or action-receipt recovery), renews no heartbeat or lease and writes nothing. `connected` is the same liveness the full getters report (a fresh workspace worker for owner/company, a fresh chat worker holding the purchase's current source account).

Work in progress is judged from the job's own native deadline, never from a worker heartbeat (`shared/finance-navi-status.mjs` `naviWorkState`, evaluated on the server at `observedAt`). For `working` (a reply or research job held by a claim), `confirming` (the draft save after the owner's confirm) and `applying` (a research report being applied), the projection reads `leaseUntil` and `attempts` — never `lease` — and returns `work`: `active` while the deadline is ahead (the only state the native finish, renewal and lock accept), `expired` once it passed (the next claim of a live worker may take the job over: `claimAssistant`, `claimCompanyAssistant`, `claimChat`, `claimResearch` reclaim with attempts < 2), `exhausted` once it passed after the last allowed claim (attempts ≥ 2: those claims record a failure next), `missing` when such a state has no deadline (no claim takes it over); `null` for every other state. `state` stays the raw native state. A passed deadline is not proof that a business effect failed or must repeat, and status never sweeps, recovers, renews or writes it: the native claims and the full getters keep doing that.

The purchase `research` entry exists only while the research row's current `requestId` was started by a live, visible (not withheld) turn of this segment: `{id, requestId, reportVersion, state, work, turnId, available, unread}` (`work` from the research row's own deadline; a fresh chat worker says nothing about it). A manual request from the research form, a report of a previous segment (after "新しい会話") or one linked to a turn withheld for another company is not a chat arrival and stays a research-page record. This is the selected conversation's status, not an inbox of other companies, purchases or pages.

An acknowledgement body is exactly `{conversationId, segment, replies?:[{turnId, replyVersion}] (1–50, unique), research?:{researchId, requestId, reportVersion, turnId}}` (research on the purchase route only); anything else is 400. The service rereads the conversation for the authenticated identity: the id and live segment must match, every named turn must be the live readable (masked) turn with exactly that `replyVersion`, and a research acknowledgement must name the row's current request, its exact report version and the live linking turn. Otherwise 409 with no effect. The write is one `updateOne` on that conversation with `$max` on the named turns only (array filters and `$elemMatch` repeat the turn id, version, saved reply and company-visibility conditions), `{timestamps:false}`, no `$inc`: the conversation revision, `updatedAt`, state, lease and actions are unchanged, so a reader's own acknowledgement never stales their next send, and nothing else (research row, draft, ledger) is written. A delayed acknowledgement cannot lower a newer seen version; a reply that finished during the request has its own turn and stays unread; parallel tabs acknowledge their own turns; after a new chat the old segment's acknowledgement is 409. The response is the fresh status plus `acknowledged`.

**Guard:** the status/read access and validation above are a new guard. It is reported plainly for the independent final review (Fable 5.1); it is not a financial approval or confirmation step.

## Browser

- `composables/useNaviStatus.ts` (used by `AssistantPanel.vue`): reads the status of the conversation the launcher opens — the company conversation on company pages; otherwise the target purchase, or this page's purchase while the target is the workspace (exactly what `summon` opens); otherwise the owner workspace — every 4 s, before any transcript mounts. Key = realm, actor, token-selected company and purchase; a token refresh keeps it. Paused while the chat is open, locked, signed out or the tab is hidden (`visibilitychange`); refreshed on return, unlock, close and reconnect. Each read goes through `ensureFreshToken` and the app's single-flight session fetch; a response is dropped when a newer read started, the key changed or the status was written since (an acknowledgement, a new chat, a scope change), or when the server's scope echo differs. 401/403/404/409 clear that key's status and stop its reads until a later authorized refresh (tab shown again, reconnect, close, unlock, renewed token or organization list, another key); other failures show "unknown". No status failure signs anyone out or adds a financial hold.
- `stores/assistant.ts`: memory-only `naviStatus {key, status, unknown}` and `naviStatusSequence`; an older server observation of the same key loses; `identify()` still resets it with everything else per owner. Nothing is persisted.
- The indicator (`[data-navi-status]`, kinds new / queued / working / interrupted / reconnect / failed / unknown; nothing when idle) is a small static pill inside the launcher button's own box (top-right), hidden with the launcher while open. The button keeps its transparent, uncircled character, size choices, greeting motion, focus and the reserved gutter; its accessible name and a polite live region (`[data-navi-status-live]`) name the conversation ("画面についての会話", "<company>の会話", "この購入の会話") and the state. Labels come from server facts only; no percentage. Unread replies come first. Progress ("回答を作成しています", "下書きへの反映を確認しています", "調査しています") is shown only for `work: active`. An expired reply with a fresh worker is "中断" (waiting for the worker's claim to take it over), without a fresh worker the existing "接続待ち"; an exhausted or deadline-less reply or research job is "中断" pointing to the open chat; an interrupted confirmation or report apply is "要確認" ("会話を開くと確認します": the open chat's existing `getChat`/`researchView` recover it and show the native outcome). An active apply still shows nothing, as before. A reply's state says nothing about its actions; their receipts stay in the chat.
- `composables/useNaviReplyVisibility.ts` (used by `AssistantConversation.vue` and `PurchaseChat.vue`): only a live reply's own text element (`data-navi-reply`, carrying the exact versions it renders) or the linked research result's summary can be acknowledged, and only while the caller says the chat view is shown for the actor/company/selection the data was loaded under, the panel is open and the tab visible. The avatar, header, history, memory, minimized, off-screen and covered text never count. The check intersects non-whitespace text ranges with both the transcript and viewport, then hit-tests those clipped rectangles. Blank lines or unused paragraph space do not count; an actually visible part of a long reply does (no whole-element threshold). A page modal, sheet or menu covering that text prevents acknowledgement. The check repeats every 250 ms while an acknowledgement is pending (an overlay that closes is noticed) and needs 0.5 s of continuous visibility. A 400/409 is not retried until the transcript reloads.
- Scrolling: an unsolicited reply or research completion follows only a reader already at the latest (the research result is brought to its start, as before). An older reader keeps the exact position and gets a "新しい回答 ↓" control inside the transcript that jumps to the replies that arrived meanwhile. Explicit send, retry, confirmation and new chat still scroll to the latest. A new chat clears the status so older segment metadata is not repainted; it acknowledges nothing.

## Verification and limits

`scripts/zoomer-fixtures/omf-navi-status.mjs` runs `scripts/finance-navi-status-integration.cjs` (owned MongoMemoryServer, the built app on loopback, synthetic people/companies/cards/statements, simulated worker replies and research results) with six native groups — owner workspace, company, purchase + research, company-teaching masking, races, work deadlines (active / expired with a fresh worker / native takeover / exhausted → native failure / missing deadline for replies, confirmation, linked research and report apply; purity; no lease in the response; the full getters still recover) — and seven installed-Chrome groups in `scripts/finance-navi-status-browser.cjs`: the layout first (390/768/1024/1365/1440 widths, two short heights, the three sizes, reduced motion, open/closed; launcher, dock and content boxes equal to the same measurement of the preserved 12cf98c release on the same loaded owner rows); closed arrival before any transcript and the queued/reconnect/working/interrupted/new/failed lanes, including a claim whose deadline passed with the worker fresh; an older reader, history, memory, minimized and tall replies; a genuine hidden tab (another tab brought to the front), the app's lock broadcast and unlock, and sign-out by a real second tab of the same origin (Chrome's own storage event); a late status read of the previous company, a removed and a restored membership; the purchase reply and linked research arriving while closed, a real page modal covering Navi, and apply; and a reply whose visible part holds only its internal blank lines (not seen) until its text is wheeled into view (seen). Before the main run it measures the 12cf98c release's layout of the same page (layout only, no status coverage). It then runs a byte-for-byte copy of the build (positive control) and one compiled defect at a time (versions on failure, any-version and revision-raising acknowledgements, a heartbeat-renewing status, a recovering status, unmasked counts, unlinked research, apply as a new arrival, hidden-tab, covered and older-reader acknowledgement/scroll, a stale scope response, a status that ignores the native deadline, a launcher that ignores the work state, visibility from the reply's whole block rectangle); each must fail at its own named assertion.

Measured and inherited, not introduced: at 768×1024 the page is 1 px wider than the viewport at every Navi size on both 12cf98c and this build; the overflowing box is the app header's control row (`components/common/AppHeader.vue:17`, 392–769 px).

Not covered: model quality, production reliability rates, a physical phone keyboard, Safari, an operating-system screen lock (only the app's own lock broadcast), server-side token revocation on sign-out (the second tab clears the local session only), more than one server instance, and the full-suite combined replay (separate). The visibility contract means "the text was on screen", not that it was read and understood.

Unchanged lanes: financial actions, the action journal and receipts, grants, claims and leases (F2/F3 continuity), the F1 admin refusals, archives and history readers, research apply/supplier/attachment validation, draft and ledger writes, worker capabilities and the model.
