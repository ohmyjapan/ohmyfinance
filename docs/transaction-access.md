# Company transaction reads

Native transaction list, detail, both statistics entry points and exports require the selected active company and fresh membership using `calendarCompany`. Owner, admin, member and viewer retain reads. A platform operator has no implicit membership exception in these entries. Unauthenticated requests fail authentication; missing/removed/inactive company membership returns 403. A foreign, unassigned or absent detail returns 404; malformed IDs return 400.

The shared service requires a server-supplied ObjectId. Every root query and statistics aggregation filters the explicitly persisted `organizationId`; client query parameters cannot replace it. Each of seven populate paths uses the same filter and its actual imported model, so a cold server does not depend on another route registering the models first. Own references retain the original field projections; foreign, unassigned and string-valued ownership references become null. Existing filters, sorting, totals, ratios and CSV/Excel/JSON formats are preserved. Responses use no-store and scoped query failures use fixed client text and fixed service logs.

Callers: `useTransactions` uses list/detail and unwraps the list's existing `{ transactions, total }` response. `ReceiptMatchDialog` also requests the list. Its current array assumption does not match that existing response; this read prerequisite does not repair or certify the dialog UI. Statistics and export routes use the same mandatory company readers. All native callers of these three service reads are included; direct Transaction model readers elsewhere are not.

No ownership field is added to schemas. Existing transaction/reference schemas and writers do not establish company assignment: unknown ownership is preserved in storage and excluded from these reads, never inferred from a card, merchant, client or amount. This candidate must not be presented as a usable migration or a complete tenant release. Generic CRUD/import/bulk, receipt matching, restore/backup, analytics, PDF, attachments, Navi company turns/history, global reference APIs and infrastructure/key/runtime custody remain open. Raw values already embedded in an assigned transaction are not independently verified against another company's documents.

Verification uses the built native HTTP server, disposable Mongo process, native synthetic account registration and company selection. It covers all legitimate member roles, explicit/foreign/missing/string assignment, seven populated references, filters, exports, both statistics shapes, actual Mongo query filters, live revocation/inactive company, concurrent company requests, restart and no financial/reference/action writes. Fault injection and meaningful compiled mutants must fail specific behavioral assertions. No production/historical/customer records or paid model/provider calls are used. These checks do not establish a reliability percentage, crash-during-write recovery, full UI privacy, historical compatibility or deployed behavior. Independent guard review and final deployed replay are still required.
