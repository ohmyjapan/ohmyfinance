# Amex statement connection

The `/connections` page keeps Amex account configuration, original statement files, source rows and ledger-review decisions together. It supports Amex Japan's eight-column transaction CSV. A Windows collector runs on the user's PC with installed Google Chrome; the hosted OMF application receives files and serves the review screen.

## Setup

The same flow serves the owner's PC and a customer's PC. Nobody installs Tailscale, copies an OMF address or pastes a token.

1. Add an Amex account in **カード連携**, using its five-digit CSV card identifiers. Group supplementary cards under their parent account. The CSV's leading hyphen is preserved in the original fields and removed for account matching.
2. Stage the downloader package for your OMF site: `node collector/package/stage.mjs --into <empty dir> --origin https://your-omf-host` (or `OMF_COLLECTOR_PUBLIC_ORIGIN`). The package carries `collector/omf-config.json` with that HTTPS origin, covered by the manifest and catalog; the server must run with the same `OMF_COLLECTOR_PUBLIC_ORIGIN`. Windows and Node 22.12.0 or newer are required on the PC. Start the package with the printed `pm2 start … collector/run.mjs` line (no flag: background starts never open a window) and open the setup page with the printed `node … collector/run.mjs --open-setup` line, which opens the running instance's page once.
3. On the setup page press **Connect to OMF**. OMF opens in the browser at `/collector-connect`: enter the OMF email, password and enabled verification code once, choose the cards this PC may fetch, confirm the PC name (defaulted from the computer name) and press 接続する. The browser returns to the downloader, which completes protection on its own. There is no separate Enable protection or Approve PC step and no OMF session is left on the PC.
4. Save each Amex login once on the setup page. It is encrypted on the PC and never sent to OMF. The page states whether login codes are read from a mailbox or must be typed: every download runs in a fresh Chrome profile, so Amex normally emails a login code; without saved mailbox access a person enters it in the Chrome window. The raw Gmail OAuth fields remain support tooling; a customer-grade mailbox consent is separate release work.
5. Choose **確定明細を取得** in OMF. The connected PC resumes automatically after a collector restart; no approval is needed per download. Keep the PC signed into Windows, awake and unlocked. The collector launches installed Chrome with an isolated profile. Complete any unrecognized issuer challenge in that window. A successful file appears in the review list; downloading does not post expenses.
6. Review the rows and choose which spending to register. Possible legacy matches can be linked without modifying the existing transaction. Repayments and unresolved credits remain in the source evidence for later reconciliation.

The setup listener binds only to `127.0.0.1:47831`, checks Host/Origin, and requires a random per-launch setup key for private endpoints. The link changes on restart. It must not be shared or published. The local setup screen does not expose saved passwords. `OMF_COLLECTOR_DIR` and `OMF_COLLECTOR_PORT` override its private directory and port; `OMF_COLLECTOR_ORIGIN` overrides the packaged address for isolated tests and staged deployments. The packaged address is used only by an unconnected installation; a connected one keeps its saved address, and a new package never changes it silently.

### How the connection is authorized

The downloader sends a token-less request bound to its installation ID, generation, device public key, remembered-PC digest, a state value, a PKCE challenge and a loopback callback on `127.0.0.1`; the request is journaled under DPAPI before it is sent. The public page shows only the PC name until the fresh password and enabled MFA check succeeds (ordinary lockout and audits apply; a trusted-device skip or a refreshed JWT cannot authorize it). Authentication returns a random request-scoped proof held only in page memory (stored as a digest, five minutes) and the owner's eligible cards. Approval needs that proof, the exact Origin, an unchanged password/MFA state and live card scope; it reserves the collector, seals the collector token and first grant into an AES-GCM capsule whose key is RSA-OAEP wrapped to the installation public key, with request, origin, installation, generation, owner, collector, cards and PC name as additional data, and creates the collector row from the reserved ID. The loopback code is exchanged with the PKCE verifier for the capsule within a bounded window; a duplicate exchange returns the same capsule, never a second credential. The downloader opens the capsule with its DPAPI private key, saves the connection and journal, acknowledges with the delivered token and remembered-PC secret, and activates the protected store with the existing owner broker and canary. Mongo stores digests only; the capsule, code and proof are cleared at acknowledgement, and an unclaimed, cancelled or expired preparation revokes only its own reserved collector, grant and installation.

Interruptions: before the browser returned, the setup page offers **Resume connection** (same request, same callback port); after the code arrived, the downloader finishes on its own, including after a restart; a lost response at the exchange or acknowledgement is retried inside the window; an expired request offers a fresh Connect. Lock cancels a pending connection. A delivered connection is ended with 接続解除 in OMF.

### Moving the owner's PC to the public address

Saved logins bind to the OMF origin, so the existing private-address installation is not migrated. After the final public origin is configured: confirm no job is queued or running and the old outbox holds only acknowledged statements, start the staged package on a fresh private directory (`OMF_COLLECTOR_DIR`), connect it through the public page, type the card logins once, stop the old collector process and keep the old directory untouched as the archive. Real issuer behaviour on the fresh-profile package is unproven until that first connected download runs with the PC unlocked and a person at it or mailbox access saved.

The owner's transition, in order (each step names what it depends on and the input only the owner can give; nothing here is code):

- **B1 Public endpoint.** Depends on: the `omf-connect` Cloudflare tunnel and its DNS name `connect.ohmyjapan.com`, which exist; the hosting machine runs no `cloudflared` yet. Install cloudflared as a service from `deploy/collector-ingress.example.yml` (hostname → `connect.ohmyjapan.com`, every rule → `http://127.0.0.1:8080`, the final 404 rule kept). Owner-only input: the Cloudflare dashboard login and the tunnel token. Accept: `curl -sI https://connect.ohmyjapan.com/collector-connect` answers 200, `/connections` answers 404, `node scripts/check-collector-ingress.mjs` is green, and the three recorded redirect cases still pass.
- **B2 OMF environment.** Depends on: B1. Give the PM2 `OhMyFinance` process `OMF_COLLECTOR_PUBLIC_ORIGIN=https://connect.ohmyjapan.com` and `OMF_TRUST_CLOUDFLARE_LOOPBACK=1`, then restart it with the deploy procedure. Accept: `GET /api/finance/collector-security/requests` through the host no longer answers 503 `OMF collector approval is not configured yet.`
- **B3 Package.** Depends on: B2 and the deployed revision. `node collector/package/stage.mjs --into <dir> --origin https://connect.ohmyjapan.com` on the collection PC. Accept: the catalog is present and `collector/omf-config.json` carries exactly that origin.
- **B4 Owner collector.** Depends on: B3. Start the staged package on a new private directory (`OMF_COLLECTOR_DIR=%LOCALAPPDATA%\OhMyFinance\collector-public`) under a new PM2 name, open the setup page once with `--open-setup`, press **Connect to OMF** (owner-only input: OMF email, password, verification code, the card selection and the PC name), save the My APLUS login once (owner-only), and enter the tablet serial under **SMS code source** (owner-only: the tablet connected by USB with debugging allowed; `adb devices` shows the serial). Accept: `/status` reports `protected:true`, `unlocked:true`, `mode:'protected'` and `smsSource.serial`; `financecollectors` holds the new row.
- **B5 Old collector.** Depends on: B4 having claimed a job. Stop the previous `OhMyFinance-collector` process only then; keep the legacy directory (`%LOCALAPPDATA%\OhMyFinance\collector`) untouched as the archive. Its card logins do not move automatically (the same-origin rule below); the new collector can import them only through the explicit **Previous card setup** check and confirm described under [Previous card setup on the same PC](#previous-card-setup-on-the-same-pc), which reads the archive without changing it. The unfinished in-place legacy transfer, the installer and signing stay in their own goal; this path does not need them.

One scheduled day with 自動取得 on for the owner's Aplus account: the job is queued at the configured hour, claimed by the new collector, reaches `verification_required`, the code is typed from the tablet with no keystroke by a person, and the job completes. Evidence: the `financialaccounts` row history, the `financeimports` count (+0 or +1), one key in `used-sms-messages.json`; then the seven-day read-only observation.

### Previous card setup on the same PC

A connected collector on a new private directory can take over the card logins the previous downloader of the same Windows user saved in its own directory (`%LOCALAPPDATA%\OhMyFinance\collector`, the pre-protection `credentials.dpapi`). The setup page shows a **Previous card setup** section only when that directory exists; nothing is read until the person presses **Check previous logins** inside a connected (protected) session with no other collector action running, and nothing is saved until they press **Use these logins on this PC** for that exact check (`collector/legacy-card-import.mjs`, local routes `POST /legacy-cards/preview` and `POST /legacy-cards/import`).

- **Grant before read.** The check first asks OMF, under the session's current collector grant (`POST /api/finance/collector-security/legacy-owner` with an empty body), for the grant's owner, origin and permitted card accounts; a revoked or expired grant, a removed PC or another owner/origin stops it before any byte of the previous directory is read. Startup, the background tick and a disconnected or manual session never touch it; `/status` only lists it — its file names, the saved-login blob's size and type, and the plain pairing marker `vault-state.json` an old /pair may have left — and never reads or decrypts that blob.
- **Which directory.** Only the standard previous directory of the Windows user running the collector, never a submitted path and never the collector's own directory. It and its blob must be ordinary files (no link, junction or other reparse point), private to that user and SYSTEM (checked read-only), and a raw previous setup: a directory that already holds protected storage (a connection, journal, device key or trust file, sealed entries, an archive or a protection state) is refused unchanged.
- **Owner proof across addresses.** When the previous setup holds a collector token, the collector hashes it locally and sends only that SHA-256 to the current OMF address under the same grant. OMF answers whether the hash is a collector of the same owner in the same database, and which of its card accounts the current grant and PC may use now (grant ∩ PC ∩ live, active, owned Amex/Aplus accounts ∩ the old collector's cards). The old collector is identity evidence only: it may have been disconnected since, and nothing about it is restored or trusted beyond its owner and card list; the authority is the CURRENT active grant, checked before anything is read and again after the lookup (a revoked or expired current grant stops the check before the read). That proof is the only link between an old HTTP address and the new HTTPS address: the old address is never contacted, rewritten or trusted by name, and the token itself never leaves the PC. A previous address without a token cannot be proved; a previous setup with neither keeps the existing protection mapping (the connection's permitted cards). Unknown and foreign tokens give the same "not confirmed" answer with no account data.
- **What moves.** Each Amex login maps to exactly one permitted live Amex account by its primary card; the one shared Aplus login only when exactly one Aplus account is permitted (saved as that account's own entry); the mailbox grant only when its mailbox is the configured login-code mailbox of a matched Amex account. Unmatched, ambiguous, incomplete and unproven logins are listed as such and stay entered by hand. Yayoi and bank logins, the old token and address, pairing, keys, markers and account metadata are never imported. A login already saved on the new collector is kept, never overwritten — for an Aplus account that includes a shared My APLUS login saved by hand while the import was running (the check and the save share the store's writer lock). The setup page's My APLUS section then names the Aplus accounts that have their own saved login (their downloads use it instead of the shared one) rather than asking for a login again.
- **How it is saved.** Each login is sealed exactly like a hand-entered one (the per-account or mailbox binding, the OMF key registration and read-back, the sealed value opened back and compared) under the store's writer lock, one at a time. Lock, Pause, a Windows lock, expiry or revocation stops before the next login; what was saved stays and a new check continues with the rest. The confirm re-proves the grant and the owner, re-reads the previous blob and refuses if its bytes changed since the check. No plaintext is written anywhere; the previous directory is never written, moved or deleted.
- **What is shown.** Account names, providers and outcomes, and counts — never a login, address, token or digest. Failures are fixed messages that name the next step (normally: enter the login in the card's own section).

Until the owner runs this check and confirm on the actual PC and a fresh card job completes there, the import is source-verified only (synthetic data, owned temporary directories and databases); no actual previous-login import or live issuer download is claimed here.

### Card downloads in the background

Amex and Aplus jobs use the background owned Chrome the bank jobs use: stock Chrome with the same sandbox, pipe transport and no debugging port, started without a window of its own; the card page opens in an inactive window that Chrome minimizes at once (restore bounds off-screen) and receives input only through DevTools, so a routine download never takes the foreground or moves the cursor. Only the card jobs ask for the minimized window: the bank jobs keep their inactive off-screen window that is not minimized and get no focus emulation, because Chrome 155 does not show a client-certificate chooser (池田泉州銀行) while the page is hidden and the hourly balance check never shows its window. The card window is minimized because an inactive normal window, even off-screen, can still be handed the foreground by Windows: a native test once sampled the foreground on the owned Chrome while the statement code was read, although Chrome 155 requests no activation there. Chrome shows the new window inactive once at its default bounds (about 20 ms in the native tests) before moving and minimizing it. A minimized window's page alone would be hidden (no animation frames, IntersectionObserver or CSS transitions until the window is shown), so the card page keeps rendering through Chrome's DevTools focus emulation (`Emulation.setFocusEmulationEnabled`, an experimental protocol command): the page's own DevTools session sends it before the first navigation and stays open until the page or the browser closes, which ends it. The page then reports itself visible and focused and renders across its navigations while the window stays minimized off-screen; Chrome treats the page as being captured and does not restore, show, move or activate the window for it. If Chrome refuses the command, the job stops at page setup with "The minimized card window could not keep its page rendering", before any page is opened or a login typed. This is proven on synthetic pages in owned Chrome (headed and minimized, and headless), not yet on the actual issuer pages (live acceptance); it does not explain why the first two real Amex sign-ins stayed on the login page, which is still unknown. When the issuer needs the person (no saved login, a challenge the collector does not complete), the collector restores that same window to normal bounds on the primary screen and brings it to the front (`showWindow`); no other window is opened or touched. The My APLUS statement code stays in the background while the configured SMS source can still type it: the window is shown once only when the person must type the code — no SMS source, a failed read of the source, or the code's five-minute validity elapsed — with the same single code request, claim, freshness, deadline and cancellation rules as before. Until then OMF shows the job as running (取得中, 「My APLUSの認証コードをSMSから自動で入力します」); 「Chromeで認証が必要」 and the instruction to type the code appear only at that point. A code the issuer rejects after it was typed waits for the same validity end before the window is shown. Ephemeral profiles, ownership by the batch's broker and closure on lock, expiry or the end of the job are unchanged.

### Amex language preference

The collector starts Chrome with `--accept-lang=ja-JP,ja;q=0.9,en;q=0.8` (`collector/browser.mjs` `LAUNCH_ARGS`). Chrome takes that switch as its language preference list as given, so the Amex pages got the weights as language tags (`navigator.languages` ja-JP, `ja;q=0.9`, `en;q=0.8`, which `Intl.getCanonicalLocales` rejects; seen in owned minimized Chrome and in owned headless Chrome 155), and Chrome weighted that list again in the Accept-Language header it sent (`ja-JP,ja;q=0.9,ja;q=0.9;q=0.8,en;q=0.8;q=0.7`, owned headless Chrome 155). The Amex job alone now starts its Chrome with the plain tags `ja-JP,ja,en` (`PLAIN_LANGUAGE_ARGS`, selected only by `collectStatement` through `browserFor`'s `plainLanguages`): its pages get ja-JP, ja and en, and Chrome sends `ja-JP,ja;q=0.9,en;q=0.8`. Every other launch (Aplus, the bank jobs, Yayoi, the research reader) keeps the previous arguments, and no other switch, sandbox, window, ownership or sign-in rule changes. The recorded and owned headless language tests of `collector/test/card-background.test.mjs` cover this (fixture legs AL and F5 of `scripts/zoomer-fixtures/omf-card-handover.mjs`). This corrects a configuration defect shown on owned Chrome; it is not shown to be why the real Amex sign-ins failed: with the same correction, a credential-free empty POST from the public login form still got 403. Actual protected-account acceptance is still required.

### Amex login trace (private diagnostics)

The first real Amex sign-ins of this downloader stayed on the login page and nothing showed why. Each Amex job therefore keeps a value-free trace of its login page (`collector/login.mjs` loginUi `trace`, written by `collectStatement`) without changing the sign-in: the same single password submission, mailbox and code rules, deadlines, statuses and handover to the person after 150 s.

- **What it records.** Fixed categories, booleans, small counts, milliseconds and allowlisted HTTP statuses only. Before typing: whether each field and the ログイン button are present, visible, enabled, editable and attached to the page's React. Before the click: whether the fields match the intended values. After the click and in later after-phase samples: the click, submit and invalid-event counts (zero means observed zero; null means unavailable). Main-frame navigation, load, fixed page flags, verification steps and the handover are also recorded. There are at most 200 events and eight page samples per phase. No login value, code, digest, nonce, length or part of a value, URL, query string, header, cookie, body, title, page text, error text or screenshot enters the trace.
- **Value comparison.** The expected values stay in the protected downloader during this additional comparison. An isolated browser function first checks the exact login origin and path, then returns transient SHA-256 digests of the current fields' UTF-16LE code units under a fresh nonce. Node compares those with its own digests and emits only match booleans. Neither expected plaintext nor its digest is passed to a browser context, whose numeric identifier can be reused after navigation. Digests and nonce are never recorded. A replaced context, unavailable WebCrypto or malformed answer leaves the comparison unknown and the sign-in continues normally; Runtime reporting and the existing browser behavior are unchanged.
- **Network observations.** The observed public login module's exact endpoint on the www or global origin is classified as `login-api`; other traffic remains separate. Its OPTIONS preflight and POST request, response and failure events have their own counters and a 40-event allowance, alongside up to 60 ordinary document/state-changing response or failure events within the total cap. A request event and its `sent` counter mean a browser request attempt, not proof that Amex received a password. A response identifies the observed HTTP status; a failed preflight with no POST response is distinct from a login response. Unrelated analytics errors are not authentication rejections. Events retain Puppeteer's arrival order, which can report an intercepted preflight failure before its request event. No request/response bodies or headers are read for these observations.
- **Network detail of the login request.** The six login POSTs of the first traced real job failed with no answer the page saw, which alone cannot tell an answer Chrome withheld because of CORS from no HTTP answer at all. For `login-api` requests only, the trace also reads Chrome's own network events through passive listeners on the page's existing DevTools session, where Puppeteer already enabled them: no command is sent on that session, no protocol domain is enabled, nothing is intercepted and the session is never detached. The end event's `network.detail` lists up to 24 such requests in order of first sight (all are counted): method, phase, milliseconds, the HTTP status the page saw and the network stack's status (`responseReceivedExtraInfo`, which Chrome sends even when CORS hides the answer from the page), each as an allowlisted status and its class, finished or failed, and the CORS error and blocked reason as fixed protocol values (`devtools-protocol` 0.0.1367902, pinned with the SDK; a newer value is `other`). Chrome's request ids only associate these events in memory (bounded, cleared at the end) and are never recorded; headers, cookies, bodies, error text, the CORS `failedParameter` and URLs are not read into it. A network-stack 403 with `MissingAllowOriginHeader` on a failed POST means a server answered and Chrome withheld the answer from the page; a failed request without a network-stack status got no HTTP answer that Chrome reported on the page's session. Neither proves an authentication result or the issuer's reason. Without that session the detail reports `listening: false` and nothing else.
- **Where.** One file per job, `<collector directory>/diagnostics/amex/<accountId>/<jobId>-<ms>.json` (schema `amex-login-trace-1`), inside the private directory like the bank diagnostics. It is written after the trace's listeners and DevTools session are stopped and before the owned Chrome closes; when a lock or another cancellation closes Chrome first, the trace is stopped and written right after. The 20 newest records of each account are kept. It is not part of the outbox, never uploaded and not served by the setup page; it is read on the PC.
- **Best effort.** Every trace step is bounded (1.5 s; stopping and writing together 5 s) and ignores its own failure; a trace that cannot run or be written leaves the job as it would have been without it.

Verification uses fictional values on synthetic pages and on the public Amex form with networking disabled before input and submission; these checks include owned headless and minimized Chrome. The network detail is also checked in owned headless Chrome against an owned loopback TLS server that answers the two Amex host names inside that Chrome only (a preflight answered 200 and a POST answered 403 without the CORS grant). They do not establish that a real account login or statement download succeeds. Actual protected-account acceptance is still required.

## Storage and recovery

- Bank logins and the optional mailbox grant use local AES-256-GCM ciphertext. The RSA-wrapped data keys reside in OMF; the local RSA private key is automatically protected by Windows CurrentUser DPAPI. No Windows Hello, PIN, biometric or TPM setup is required. Entries bind installation, generation, OMF origin, owner, provider and account. Bank passwords, mailbox refresh tokens and the private key are never sent to OMF. This does not hide uploaded accounting transactions from the existing hosted service.
- The approved PC stores a separate random device credential under CurrentUser DPAPI; OMF stores its digest bound to the initial password/MFA approval. Together with the scoped collector token, it silently obtains short-lived key-access grants. Those grants and wrapped data keys are not persisted locally. Disconnect the PC in **カード連携** to refuse subsequent renewals and key reads. Changing the OMF password or MFA settings also requires reconnecting. Account scope is checked again at key release. Revocation cannot erase secrets already delivered to the PC.
- **Enable protection** obtains OMF approval before opening the legacy vault. It encrypts and verifies every retained entry, rewrites the old blob without bank/mail credentials and activates the new generation. Interrupted migration can resume with the remembered PC credential after its initial approval. The encrypted legacy copy is retained for recovery; prior backups and retained browser profiles are not erased. Pending statements retain their verified owner/origin binding.
- Automatic migration requires the same OMF origin and owner. Existing HTTP installations are not silently transferred to a new HTTPS address. Use a separate private collector directory and reconnect its bank logins for an HTTPS pilot; preserve the original directory and pending statements. The only cross-address move of card logins is the explicit [previous card setup](#previous-card-setup-on-the-same-pc) import, proved by the same-owner same-database token hash; outbox files and bank logins never move. Replacing a token for the same owner and origin reconnects the installation even if migration was interrupted; an unfinished protection reset must finish first.
- The collector remains ready after a completed batch and renews access silently. **Pause** (including the local lock action) persists across restarts; **Resume** does not request another approval unless the trusted connection needs repair. Windows lock, sign-out or sleep closes the current browser session; automatic syncing waits for an available desktop. Offline failures leave work queued and retry later without opening an approval browser. Explicit cancellation does not authorize a connection.
- Each batch launches owned, sandboxed Chrome using a pipe with no TCP debugging listener. Profiles under `profiles/ephemeral/` are specific to owner, provider, account and batch; they are removed after closure and recovered after crashes. Existing Chrome windows and retained profiles are never attached or reused. A Windows job object ends owned browser processes if their broker dies. Keep one collector instance per private directory.
- The private directory grants access to its Windows user and SYSTEM. Startup verifies permissions before exposing setup; protected access refuses elevated execution. Remembering a PC intentionally permits unattended access by its Windows account. Malware controlling that account, an administrator or the OS is outside this protection; this is not a promise that same-user software cannot read saved access. Local files and cloud records separately remain insufficient without their respective access authority.
- Manual mode stores no bank passwords. Connection changes and a protection reset use fresh OMF authentication. A missing local key requires reconnecting bank logins. Typed **RESET** records a pending recovery and moves sealed entries into an archive, without deleting them. No lost private key is required to authorize reset. An unfinished reset remains visible and must finish before saved logins can be used.
- Customer release requires a configured `OMF_COLLECTOR_PUBLIC_ORIGIN` with valid HTTPS, a package staged with the same origin, signed delivery, completed acceptance and the authorized independent review. The customer package excludes diagnostic exporters and test brokers. An unsigned package is a test artifact, not a customer release. Still open before customers: a signed installer with bundled runtime, auto-start for a normal user, a setup shortcut, PowerShell execution-policy compatibility on a default Windows client, clean-machine acceptance, and a consent-based mailbox setup. The legacy token-based pairing (`POST /api/finance/collectors`, the setup page's Enable protection for a previous-format directory, pair/batch/reset approvals) remains for existing installations and is not the customer path.
- Downloads are verified against the selected card, complete statement row count, expected headers and registered card identifiers before upload. The collector keeps original bytes and a manifest in its private outbox. A pending upload retries before another browser download. Acknowledged files remain available locally.
- Hosted originals are stored under `OMF_DATA_DIR/imports`, defaulting to `~/.ohmyfinance/imports`, by SHA-256. The archive uses a completed temporary file and an atomic hard link; a partial write cannot be accepted as a complete original.
- MongoDB collections `financialaccounts`, `financecollectors`, `financeimports`, `financeentries`, `financedrafts`, and `financedocuments` hold mappings, scoped token hashes, source data and stable transaction references. Back up these collections together with `transactions` and the complete private evidence directory (`OMF_DATA_DIR`, including `imports` and `documents`). The older OMF JSON backup/restore screen does **not** include this new evidence set. Use a full MongoDB backup plus the evidence directory; do not treat the old JSON export as a full connector backup.

## Repeat protection

File hashes are unique within an account. Normalized transaction fingerprints include both dates, original card identifier, signed amount, description and foreign-currency information. Occurrence numbers preserve legitimate identical purchases within a complete snapshot. Repeated snapshots of the same coverage reuse posted entries. Other coverage, changed processing/currency information and historical ledger matches require review. Deferring a row never clears its duplicate warning.

Ledger posting reserves a stable transaction ID before insertion and renews an account-level lease. Retrying after a process interruption updates that same transaction ID. A concurrent reviewer receives a conflict or sees the already-posted result. Request decisions are validated before writes begin; infrastructure failures can leave partial progress, which the review screen reloads and resumes. Linking records evidence without rewriting existing accounting data.

## Current scope

Amex and Aplus collection is user-triggered by default. Either can also run on a daily schedule: 自動取得 in カード連携 switches it on per account with a JST hour, the server queues one job per JST day once that hour has passed and no job was queued or attempted that day (a day the PC was off catches up with one job when it is next available; a running job with an expired lease is continued, never re-queued), and `OMF_SYNC_SCHEDULE_MS` sets the server's check interval (`0` disables the schedule). The same daily schedule also serves an active Amex account whose 自動取得 is on, with the same once-per-JST-day, catch-up, manual-job and lease rules; an Amex job downloads only the latest CLOSED statement (a day before the next statement closes downloads the same statement again, which the import accepts as the same file), never unbilled activity. The 自動取得 setting of an Amex account is switched on only by a person in the カード連携 control (`PUT /api/finance/accounts/:id/auto-sync` accepts Amex and Aplus accounts); existing Amex accounts stay off until then. The owner Navi action still sets Aplus accounts only. When the downloader has an SMS code source (the tablet serial under **SMS code source**, read through adb), it types the one statement code that matches the request within the code's five-minute validity; otherwise a person types it in Chrome. Every run reads Amex's available statement links, explicitly opens the latest end date before today in Japan, and verifies the displayed start/end dates, signed-in card and complete row count. It never relies on the default activity page, which can show current unbilled activity. An empty, ambiguous or incomplete statement stops the download for attention. The same 確定明細を取得 button serves Aplus accounts: the downloader signs in to My APLUS, downloads every finalized statement month OMF does not already hold (each verified against the signed-in card, the selected month and the displayed お支払金額 before upload, one SMS statement code per month typed by the downloader from the configured tablet or by a person in Chrome) and captures the current unbilled page as a pending import that the finalized statement later settles; see [Aplus credential setup](aplus-credentials.md). Amex unbilled activity and refund accounting need their own verified provider behavior before activation. This is not an instant bank feed. No purchase, payment or transfer action is performed.

With an authorized Gmail OAuth connection sealed locally and opened during an unlocked batch (`clientId`, `clientSecret`, `refreshToken`, `mailbox`), the collector can complete the verified Amex **account-login** email challenge. It selects the configured masked email recipient, anchors freshness to its own email-request click, and checks the actual OAuth mailbox, original recipient, sender, exact subject, card suffix, issuance/receipt timestamps and one unambiguous code. Forwarding preserves the original recipient check. Consumed message IDs are saved locally before typing; codes are never saved. It does not change message labels or read state and is separate from payment/SafeKey mail readers. Existing challenges without a request timestamp, unknown challenges, email errors and ambiguous codes remain available in Chrome for manual completion. It never automatically resends a code or repeats a failed password submission within a job.

Real files, account mappings, profiles and credentials must stay outside this public repository. Tests use synthetic data.

## Validation

### Restricted public connector host

`deploy/collector-ingress.example.yml` is an example for a **separate** Cloudflare named tunnel on the hosting machine. Its reserved `.invalid` host is not a deployment address. Choose the host, configure HTTPS-only access and certificates, and use the same HTTPS origin for the collector package and `OMF_COLLECTOR_PUBLIC_ORIGIN`. Preserve existing tunnels. The example permits only Connect, approval/recovery login, their APIs, collector syncing and the built Nuxt assets; the main accounting application remains private. Do not expose the whole application by dropping the final 404 rule. Public self-registration and accounting pages are outside this endpoint.

When that dedicated tunnel connects to `127.0.0.1:8080`, set `OMF_TRUST_CLOUDFLARE_LOOPBACK=1`. OMF then accepts a single valid `CF-Connecting-IP` only from a loopback peer whose Host matches the configured HTTPS origin. Otherwise rate limits use the socket peer. `X-Forwarded-For` never supplies the identity. This trusts local processes on the hosting machine; keep the tunnel and its configuration under administrator control, prevent arbitrary traffic reaching a trusted local forwarder, and verify the actual edge headers before enabling public access. See [Cloudflare's header contract](https://developers.cloudflare.com/fundamentals/reference/http-headers/). Without this opt-in, tunnel visitors share the loopback request budget.

Login and the existing limited auth routes retain their thresholds, keyed by route family independent of query strings. Ordinary 2FA also reserves a durable account budget of ten attempts per fixed fifteen-minute window after validating a signed pending challenge and active MFA user, matching the connection flow's allowance. New challenges, IP changes and worker restarts do not reset that account budget. The first excess attempt in each account/window writes an auth `lockout` audit with the account, window and count, through the existing best-effort audit helper; repeated blocked attempts do not add duplicate entries. `Retry-After` describes automatic recovery; sign in again for a fresh challenge if the previous one expired while waiting. There is no manual unlock step. Include `authverificationattempts`, `usedauthchallenges` and `auditlogs` in full database backups. Counters and limit audits retain no password, OTP, pending token or email. Initial connection requests use the same verified client identity as login: separate 30-per-minute client allowances behind the configured tunnel, while retaining the 300-per-minute global cap. Legacy transaction/receipt uploads require a valid authenticated session before reading multipart content, and only their exact paths are handled.
