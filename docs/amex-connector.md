# Amex statement connection

The `/connections` page keeps Amex account configuration, original statement files, source rows and ledger-review decisions together. It supports Amex Japan's eight-column transaction CSV. A Windows collector runs on the user's PC with installed Google Chrome; the hosted OMF application receives files and serves the review screen.

## Setup

1. Add an Amex account in **カード連携**, using its five-digit CSV card identifiers. Group supplementary cards under their parent account. The CSV's leading hyphen is preserved in the original fields and removed for account matching.
2. Select that account when issuing a collector token. The token permits account status, job claiming and CSV upload for only the selected accounts. It cannot read the ledger or commit expenses. Revocation is immediate.
3. On the collection PC, run `npm ci --prefix collector --ignore-scripts`, then `node collector/run.mjs` (also use this entry point with PM2). Windows and Node 22.12.0 or newer are required. Read the private `setup-link.txt` in `%LOCALAPPDATA%/OhMyFinance/collector` and open it locally. Pair the OMF HTTPS address and collector token, then connect the PC through OMF using its password and enabled MFA. Save each Amex login locally. Existing installations migrate saved logins before protection is reported active.
4. Choose **確定明細を取得** in OMF. The approved PC resumes automatically after a collector restart; no approval is needed per download. Keep the PC signed into Windows and available. The collector launches installed Chrome with an isolated profile. Complete any unrecognized issuer challenge in that window. A successful file appears in the review list; downloading does not post expenses.
5. Review the rows and choose which spending to register. Possible legacy matches can be linked without modifying the existing transaction. Repayments and unresolved credits remain in the source evidence for later reconciliation.

The setup listener binds only to `127.0.0.1:47831`, checks Host/Origin, and requires a random per-launch setup key for private endpoints. The link changes on restart. It must not be shared or published. The local setup screen does not expose saved passwords. `OMF_COLLECTOR_DIR` and `OMF_COLLECTOR_PORT` override its private directory and port.

## Storage and recovery

- Bank logins and the optional mailbox grant use local AES-256-GCM ciphertext. The RSA-wrapped data keys reside in OMF; the local RSA private key is automatically protected by Windows CurrentUser DPAPI. No Windows Hello, PIN, biometric or TPM setup is required. Entries bind installation, generation, OMF origin, owner, provider and account. Bank passwords, mailbox refresh tokens and the private key are never sent to OMF. This does not hide uploaded accounting transactions from the existing hosted service.
- The approved PC stores a separate random device credential under CurrentUser DPAPI; OMF stores its digest bound to the initial password/MFA approval. Together with the scoped collector token, it silently obtains short-lived key-access grants. Those grants and wrapped data keys are not persisted locally. Disconnect the PC in **カード連携** to refuse subsequent renewals and key reads. Changing the OMF password or MFA settings also requires reconnecting. Account scope is checked again at key release. Revocation cannot erase secrets already delivered to the PC.
- **Enable protection** obtains OMF approval before opening the legacy vault. It encrypts and verifies every retained entry, rewrites the old blob without bank/mail credentials and activates the new generation. Interrupted migration can resume with the remembered PC credential after its initial approval. The encrypted legacy copy is retained for recovery; prior backups and retained browser profiles are not erased. Pending statements retain their verified owner/origin binding.
- Automatic migration requires the same OMF origin and owner. Existing HTTP installations are not silently transferred to a new HTTPS address. Use a separate private collector directory and reconnect its bank logins for an HTTPS pilot; preserve the original directory and pending statements. Moving historical credentials or outbox files across origins needs its own verified migration. Replacing a token for the same owner and origin reconnects the installation even if migration was interrupted; an unfinished protection reset must finish first.
- The collector remains ready after a completed batch and renews access silently. **Pause** (including the local lock action) persists across restarts; **Resume** does not request another approval unless the trusted connection needs repair. Windows lock, sign-out or sleep closes the current browser session; automatic syncing waits for an available desktop. Offline failures leave work queued and retry later without opening an approval browser. Explicit cancellation does not authorize a connection.
- Each batch launches owned, sandboxed Chrome using a pipe with no TCP debugging listener. Profiles under `profiles/ephemeral/` are specific to owner, provider, account and batch; they are removed after closure and recovered after crashes. Existing Chrome windows and retained profiles are never attached or reused. A Windows job object ends owned browser processes if their broker dies. Keep one collector instance per private directory.
- The private directory grants access to its Windows user and SYSTEM. Startup verifies permissions before exposing setup; protected access refuses elevated execution. Remembering a PC intentionally permits unattended access by its Windows account. Malware controlling that account, an administrator or the OS is outside this protection; this is not a promise that same-user software cannot read saved access. Local files and cloud records separately remain insufficient without their respective access authority.
- Manual mode stores no bank passwords. Connection changes and a protection reset use fresh OMF authentication. A missing local key requires reconnecting bank logins. Typed **RESET** records a pending recovery and moves sealed entries into an archive, without deleting them. No lost private key is required to authorize reset. An unfinished reset remains visible and must finish before saved logins can be used.
- Customer release requires a configured `OMF_COLLECTOR_PUBLIC_ORIGIN` with valid HTTPS, signed delivery, completed acceptance and the authorized independent review. The customer package excludes diagnostic exporters and test brokers. An unsigned package is a test artifact, not a customer release.
- Downloads are verified against the selected card, complete statement row count, expected headers and registered card identifiers before upload. The collector keeps original bytes and a manifest in its private outbox. A pending upload retries before another browser download. Acknowledged files remain available locally.
- Hosted originals are stored under `OMF_DATA_DIR/imports`, defaulting to `~/.ohmyfinance/imports`, by SHA-256. The archive uses a completed temporary file and an atomic hard link; a partial write cannot be accepted as a complete original.
- MongoDB collections `financialaccounts`, `financecollectors`, `financeimports`, `financeentries`, `financedrafts`, and `financedocuments` hold mappings, scoped token hashes, source data and stable transaction references. Back up these collections together with `transactions` and the complete private evidence directory (`OMF_DATA_DIR`, including `imports` and `documents`). The older OMF JSON backup/restore screen does **not** include this new evidence set. Use a full MongoDB backup plus the evidence directory; do not treat the old JSON export as a full connector backup.

## Repeat protection

File hashes are unique within an account. Normalized transaction fingerprints include both dates, original card identifier, signed amount, description and foreign-currency information. Occurrence numbers preserve legitimate identical purchases within a complete snapshot. Repeated snapshots of the same coverage reuse posted entries. Other coverage, changed processing/currency information and historical ledger matches require review. Deferring a row never clears its duplicate warning.

Ledger posting reserves a stable transaction ID before insertion and renews an account-level lease. Retrying after a process interruption updates that same transaction ID. A concurrent reviewer receives a conflict or sees the already-posted result. Request decisions are validated before writes begin; infrastructure failures can leave partial progress, which the review screen reloads and resumes. Linking records evidence without rewriting existing accounting data.

## Current scope

Collection is user-triggered. Every run reads Amex's available statement links, explicitly opens the latest end date before today in Japan, and verifies the displayed start/end dates, signed-in card and complete row count. It never relies on the default activity page, which can show current unbilled activity. An empty, ambiguous or incomplete statement stops the download for attention. Current unbilled activity, pending-to-posted reconciliation, refund accounting and scheduling need their own verified provider behavior before activation. This is not an instant bank feed. No purchase, payment or transfer action is performed.

With an authorized Gmail OAuth connection sealed locally and opened during an unlocked batch (`clientId`, `clientSecret`, `refreshToken`, `mailbox`), the collector can complete the verified Amex **account-login** email challenge. It selects the configured masked email recipient, anchors freshness to its own email-request click, and checks the actual OAuth mailbox, original recipient, sender, exact subject, card suffix, issuance/receipt timestamps and one unambiguous code. Forwarding preserves the original recipient check. Consumed message IDs are saved locally before typing; codes are never saved. It does not change message labels or read state and is separate from payment/SafeKey mail readers. Existing challenges without a request timestamp, unknown challenges, email errors and ambiguous codes remain available in Chrome for manual completion. It never automatically resends a code or repeats a failed password submission within a job.

Real files, account mappings, profiles and credentials must stay outside this public repository. Tests use synthetic data.

## Validation

Run `npm run test:finance`, `npm test --prefix collector` under the interactive Windows user, `npm run build`, then `npm run test:finance:integration`. The integration suite starts a temporary MongoDB and the built application on an ephemeral local port; it does not use production data. `npm run test:auth` covers the existing session/refresh behavior.

The existing deployment remains: commit and push from development, fast-forward pull on the hosting machine, build Nuxt, then restart OhMyFinance. Install and run the collector only on the collection PC. Preserve the finance collections, the five collector-security collections (`collectorinstallations`, `collectorapprovals`, `collectorgrants`, `collectorwrappedkeys`, `collectorthrottles`), the private collector directory and the evidence directory for forward recovery. An older collector cannot read the new split format; do not point it at the migrated directory during rollback.
