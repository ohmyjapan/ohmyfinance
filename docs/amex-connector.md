# Amex statement connection

The `/connections` page keeps Amex account configuration, original statement files, source rows and ledger-review decisions together. It supports Amex Japan's eight-column transaction CSV. A Windows collector runs on the user's PC with installed Google Chrome; the hosted OMF application receives files and serves the review screen.

## Setup

The same flow serves the owner's PC and a customer's PC. Nobody installs Tailscale, copies an OMF address or pastes a token.

1. Add an Amex account in **カード連携**, using its five-digit CSV card identifiers. Group supplementary cards under their parent account. The CSV's leading hyphen is preserved in the original fields and removed for account matching.
2. Stage the downloader package for your OMF site: `node collector/package/stage.mjs --into <empty dir> --origin https://your-omf-host` (or `OMF_COLLECTOR_PUBLIC_ORIGIN`). The package carries `collector/omf-config.json` with that HTTPS origin, covered by the manifest and catalog; the server must run with the same `OMF_COLLECTOR_PUBLIC_ORIGIN`. Windows and Node 22.12.0 or newer are required on the PC. Start the package with the printed `pm2 start … collector/run.mjs` line (no flag: background starts never open a window) and open the setup page with the printed `node … collector/run.mjs --open-setup` line, which opens the running instance's page once.
3. On the setup page press **Connect to OMF**. OMF opens in the browser at `/collector-connect`: enter the OMF email, password and enabled verification code once, choose the cards this PC may fetch, confirm the PC name (defaulted from the computer name) and press 接続する. The browser returns to the downloader, which completes protection on its own. There is no separate Enable protection or Approve PC step and no OMF session is left on the PC.
4. Save each Amex login once on the setup page. It is encrypted on the PC and never sent to OMF. The page states whether login codes are read from a mailbox or must be typed: every download runs in a fresh Chrome profile, so Amex normally emails a login code; without saved mailbox access a person enters it in the Chrome window. The raw Gmail OAuth fields remain support tooling; a customer-grade mailbox consent is separate release work.
5. Choose **確定明細を取得** in OMF. The connected PC resumes automatically after a collector restart; no approval is needed per download. Keep the PC signed into Windows, awake and unlocked. The collector launches installed Chrome with an isolated profile. Complete any unrecognized issuer challenge in that window. A successful file appears in the review list; downloading does not post expenses.
6. Review the rows and choose which spending to register. Possible legacy matches can be linked without modifying the existing transaction. Repayments and unresolved credits remain in the source evidence for later reconciliation.

The setup listener binds only to `127.0.0.1:47831`, checks Host/Origin, and requires a random per-launch setup key for private endpoints. The link changes on restart. It must not be shared or published. The local setup screen does not expose saved passwords. `OMF_COLLECTOR_DIR` and `OMF_COLLECTOR_PORT` override its private directory and port; `OMF_COLLECTOR_ORIGIN` overrides the packaged address for isolated tests and staged deployments. The packaged address is used only by an unconnected installation; a connected one keeps its saved address, and a new package never changes it silently.

### How the connection is authorized

The downloader sends a token-less request bound to its installation ID, generation, device public key, remembered-PC digest, a state value, a PKCE challenge and a loopback callback on `127.0.0.1`; the request is journaled under DPAPI before it is sent. The public page shows only the PC name until the fresh password and enabled MFA check succeeds (ordinary lockout and audits apply; a trusted-device skip or a refreshed JWT cannot authorize it). Authentication returns a random request-scoped proof held only in page memory (stored as a digest, five minutes) and the owner's eligible cards. Approval needs that proof, the exact Origin, an unchanged password/MFA state and live card scope; it reserves the collector, seals the collector token and first grant into an AES-GCM capsule whose key is RSA-OAEP wrapped to the installation public key, with request, origin, installation, generation, owner, collector, cards and PC name as additional data, and creates the collector row from the reserved ID. The loopback code is exchanged with the PKCE verifier for the capsule within a bounded window; a duplicate exchange returns the same capsule, never a second credential. The downloader opens the capsule with its DPAPI private key, saves the connection and journal, acknowledges with the delivered token and remembered-PC secret, and activates the protected store with the existing owner broker and canary. Mongo stores digests only; the capsule, code and proof are cleared at acknowledgement, and an unclaimed, cancelled or expired preparation revokes only its own reserved collector, grant and installation.

Interruptions: before the browser returned, the setup page offers **Resume connection** (same request, same callback port); after the code arrived, the downloader finishes on its own, including after a restart; a lost response at the exchange or acknowledgement is retried inside the window; an expired request offers a fresh Connect. Lock cancels a pending connection. A delivered connection is ended with 接続解除 in OMF.

### Moving the owner's PC to the public address

Saved logins bind to the OMF origin, so the existing private-address installation is not migrated. After the final public origin is configured: confirm no job is queued or running and the old outbox holds only acknowledged statements, start the staged package on a fresh private directory (`OMF_COLLECTOR_DIR`), connect it through the public page, type the card logins once, stop the old collector process and keep the old directory untouched as the archive. Real issuer behaviour on the fresh-profile package is unproven until that first connected download runs with the PC unlocked and a person at it or mailbox access saved.

## Storage and recovery

- Bank logins and the optional mailbox grant use local AES-256-GCM ciphertext. The RSA-wrapped data keys reside in OMF; the local RSA private key is automatically protected by Windows CurrentUser DPAPI. No Windows Hello, PIN, biometric or TPM setup is required. Entries bind installation, generation, OMF origin, owner, provider and account. Bank passwords, mailbox refresh tokens and the private key are never sent to OMF. This does not hide uploaded accounting transactions from the existing hosted service.
- The approved PC stores a separate random device credential under CurrentUser DPAPI; OMF stores its digest bound to the initial password/MFA approval. Together with the scoped collector token, it silently obtains short-lived key-access grants. Those grants and wrapped data keys are not persisted locally. Disconnect the PC in **カード連携** to refuse subsequent renewals and key reads. Changing the OMF password or MFA settings also requires reconnecting. Account scope is checked again at key release. Revocation cannot erase secrets already delivered to the PC.
- **Enable protection** obtains OMF approval before opening the legacy vault. It encrypts and verifies every retained entry, rewrites the old blob without bank/mail credentials and activates the new generation. Interrupted migration can resume with the remembered PC credential after its initial approval. The encrypted legacy copy is retained for recovery; prior backups and retained browser profiles are not erased. Pending statements retain their verified owner/origin binding.
- Automatic migration requires the same OMF origin and owner. Existing HTTP installations are not silently transferred to a new HTTPS address. Use a separate private collector directory and reconnect its bank logins for an HTTPS pilot; preserve the original directory and pending statements. Moving historical credentials or outbox files across origins needs its own verified migration. Replacing a token for the same owner and origin reconnects the installation even if migration was interrupted; an unfinished protection reset must finish first.
- The collector remains ready after a completed batch and renews access silently. **Pause** (including the local lock action) persists across restarts; **Resume** does not request another approval unless the trusted connection needs repair. Windows lock, sign-out or sleep closes the current browser session; automatic syncing waits for an available desktop. Offline failures leave work queued and retry later without opening an approval browser. Explicit cancellation does not authorize a connection.
- Each batch launches owned, sandboxed Chrome using a pipe with no TCP debugging listener. Profiles under `profiles/ephemeral/` are specific to owner, provider, account and batch; they are removed after closure and recovered after crashes. Existing Chrome windows and retained profiles are never attached or reused. A Windows job object ends owned browser processes if their broker dies. Keep one collector instance per private directory.
- The private directory grants access to its Windows user and SYSTEM. Startup verifies permissions before exposing setup; protected access refuses elevated execution. Remembering a PC intentionally permits unattended access by its Windows account. Malware controlling that account, an administrator or the OS is outside this protection; this is not a promise that same-user software cannot read saved access. Local files and cloud records separately remain insufficient without their respective access authority.
- Manual mode stores no bank passwords. Connection changes and a protection reset use fresh OMF authentication. A missing local key requires reconnecting bank logins. Typed **RESET** records a pending recovery and moves sealed entries into an archive, without deleting them. No lost private key is required to authorize reset. An unfinished reset remains visible and must finish before saved logins can be used.
- Customer release requires a configured `OMF_COLLECTOR_PUBLIC_ORIGIN` with valid HTTPS, a package staged with the same origin, signed delivery, completed acceptance and the authorized independent review. The customer package excludes diagnostic exporters and test brokers. An unsigned package is a test artifact, not a customer release. Still open before customers: a signed installer with bundled runtime, auto-start for a normal user, a setup shortcut, PowerShell execution-policy compatibility on a default Windows client, clean-machine acceptance, and a consent-based mailbox setup. The legacy token-based pairing (`POST /api/finance/collectors`, the setup page's Enable protection for a previous-format directory, pair/batch/reset approvals) remains for existing installations and is not the customer path.
- Downloads are verified against the selected card, complete statement row count, expected headers and registered card identifiers before upload. The collector keeps original bytes and a manifest in its private outbox. A pending upload retries before another browser download. Acknowledged files remain available locally.
- Hosted originals are stored under `OMF_DATA_DIR/imports`, defaulting to `~/.ohmyfinance/imports`, by SHA-256. The archive uses a completed temporary file and an atomic hard link; a partial write cannot be accepted as a complete original.
- MongoDB collections `financialaccounts`, `financecollectors`, `financeimports`, `financeentries`, `financedrafts`, and `financedocuments` hold mappings, scoped token hashes, source data and stable transaction references. Back up these collections together with `transactions` and the complete private evidence directory (`OMF_DATA_DIR`, including `imports` and `documents`). The older OMF JSON backup/restore screen does **not** include this new evidence set. Use a full MongoDB backup plus the evidence directory; do not treat the old JSON export as a full connector backup.

## Repeat protection

File hashes are unique within an account. Normalized transaction fingerprints include both dates, original card identifier, signed amount, description and foreign-currency information. Occurrence numbers preserve legitimate identical purchases within a complete snapshot. Repeated snapshots of the same coverage reuse posted entries. Other coverage, changed processing/currency information and historical ledger matches require review. Deferring a row never clears its duplicate warning.

Ledger posting reserves a stable transaction ID before insertion and renews an account-level lease. Retrying after a process interruption updates that same transaction ID. A concurrent reviewer receives a conflict or sees the already-posted result. Request decisions are validated before writes begin; infrastructure failures can leave partial progress, which the review screen reloads and resumes. Linking records evidence without rewriting existing accounting data.

## Current scope

Collection is user-triggered. Every run reads Amex's available statement links, explicitly opens the latest end date before today in Japan, and verifies the displayed start/end dates, signed-in card and complete row count. It never relies on the default activity page, which can show current unbilled activity. An empty, ambiguous or incomplete statement stops the download for attention. Current unbilled activity, pending-to-posted reconciliation, refund accounting and scheduling need their own verified provider behavior before activation. This is not an instant bank feed. No purchase, payment or transfer action is performed.

With an authorized Gmail OAuth connection sealed locally and opened during an unlocked batch (`clientId`, `clientSecret`, `refreshToken`, `mailbox`), the collector can complete the verified Amex **account-login** email challenge. It selects the configured masked email recipient, anchors freshness to its own email-request click, and checks the actual OAuth mailbox, original recipient, sender, exact subject, card suffix, issuance/receipt timestamps and one unambiguous code. Forwarding preserves the original recipient check. Consumed message IDs are saved locally before typing; codes are never saved. It does not change message labels or read state and is separate from payment/SafeKey mail readers. Existing challenges without a request timestamp, unknown challenges, email errors and ambiguous codes remain available in Chrome for manual completion. It never automatically resends a code or repeats a failed password submission within a job.

Real files, account mappings, profiles and credentials must stay outside this public repository. Tests use synthetic data.

## Validation

### Restricted public connector host

`deploy/collector-ingress.example.yml` is an example for a **separate** Cloudflare named tunnel on the hosting machine. Its reserved `.invalid` host is not a deployment address. Choose the host, configure HTTPS-only access and certificates, and use the same HTTPS origin for the collector package and `OMF_COLLECTOR_PUBLIC_ORIGIN`. Preserve existing tunnels. The example permits only Connect, approval/recovery login, their APIs, collector syncing and the built Nuxt assets; the main accounting application remains private. Do not expose the whole application by dropping the final 404 rule. Public self-registration and accounting pages are outside this endpoint.

When that dedicated tunnel connects to `127.0.0.1:8080`, set `OMF_TRUST_CLOUDFLARE_LOOPBACK=1`. OMF then accepts a single valid `CF-Connecting-IP` only from a loopback peer whose Host matches the configured HTTPS origin. Otherwise rate limits use the socket peer. `X-Forwarded-For` never supplies the identity. This trusts local processes on the hosting machine; keep the tunnel and its configuration under administrator control, prevent arbitrary traffic reaching a trusted local forwarder, and verify the actual edge headers before enabling public access. See [Cloudflare's header contract](https://developers.cloudflare.com/fundamentals/reference/http-headers/). Without this opt-in, tunnel visitors share the loopback request budget.

Login and the existing limited auth routes retain their thresholds, keyed by route family independent of query strings. Ordinary 2FA also reserves a durable account budget of ten attempts per fixed fifteen-minute window after validating a signed pending challenge and active MFA user, matching the connection flow's allowance. New challenges, IP changes and worker restarts do not reset that account budget. The first excess attempt in each account/window writes an auth `lockout` audit with the account, window and count, through the existing best-effort audit helper; repeated blocked attempts do not add duplicate entries. `Retry-After` describes automatic recovery; sign in again for a fresh challenge if the previous one expired while waiting. There is no manual unlock step. Include `authverificationattempts`, `usedauthchallenges` and `auditlogs` in full database backups. Counters and limit audits retain no password, OTP, pending token or email. Initial connection requests use the same verified client identity as login: separate 30-per-minute client allowances behind the configured tunnel, while retaining the 300-per-minute global cap. Legacy transaction/receipt uploads require a valid authenticated session before reading multipart content, and only their exact paths are handled.

Build first, then run the hub verifier with `scripts/zoomer-fixtures/collector-public-boundary.mjs`. Set `OMF_TEST_CLOUDFLARED` to the installed binary if it is not on PATH. The fixture checks actual built assets, deliberately broken ingress rules, upload/query dispatch, trusted proxy identity, two-worker MFA concurrency, restart persistence, cooldown and scoped collector upload retries. Its HTTP proxy uses the real offline matcher but **simulates transport**; it does not create a public tunnel or prove edge behavior. Test accounts, MongoDB and files are temporary and synthetic; no browser or bank login opens.

Before release, independently review these new guards and repeat route/asset checks on the final deployed build. Through the actual public HTTPS host, verify blocked legacy paths, the two query-string upload probes, header handling, method/body forwarding, the recovery flow, and browser/issuer acceptance. Preserve the original collector and acknowledged evidence; use a fresh private directory when changing from HTTP to HTTPS, and stop the old collector before enabling real jobs on its replacement. Signed delivery, clean-machine acceptance and mailbox consent remain separate release prerequisites.

Run `npm run test:finance`, `npm test --prefix collector` under the interactive Windows user, `npm run build`, then `npm run test:finance:integration`. The integration suite starts a temporary MongoDB and the built application on an ephemeral local port; it does not use production data. `npm run test:auth` covers the existing session/refresh behavior. `scripts/collector-security-integration.ts` and `scripts/collector-trusted-device-http.ts` (through the hub verifier fixture `scripts/zoomer-fixtures/collector-connect.mjs`) cover the initial Connect flow with synthetic users, an isolated HTTPS origin, real DPAPI and the real owner broker, every bank request intercepted; this is synthetic acceptance, not issuer acceptance or a measured production reliability rate, and no production initial-connect case exists to replay.

The existing deployment remains: commit and push from development, fast-forward pull on the hosting machine, build Nuxt, then restart OhMyFinance. Install and run the collector only on the collection PC. Preserve the finance collections, the six collector-security collections (`collectorinstallations`, `collectorapprovals`, `collectorgrants`, `collectorwrappedkeys`, `collectorthrottles`, `collectorconnects`), the private collector directory and the evidence directory for forward recovery. An older collector cannot read the new split format; do not point it at the migrated directory during rollback.
