# Trusted company transaction creation

Native `POST /api/transactions` requires the signed-in session's selected company and current active membership. It passes that ObjectId to `createCompanyTransaction`; request body/query company claims never decide ownership. The existing save flow adds the fixed field to this document with a per-path strict override before its one normal save. No schema-wide ownership field, global strict-mode change or second assignment write is introduced. Validation, zero amount, defaults, reference/timeline hooks and timestamps are retained. This company path uses fixed save-error logs/client messages while preserving the existing 400/500 distinction.

CSV import (`POST /api/transactions/import`) now uses the same trusted path: fresh selected-company membership first, then `createCompanyTransaction` with a company-scoped duplicate check (final review F1). Restore writes only rows recorded for the selected company through the same `strict:false` setter (F2). See [company import and restore](company-import-restore.md). `createTransaction` (no company) still exists but no native route calls it after this change; the service's `importTransactions` and other legacy writers are unchanged. Card posting, bank import, recurring generation, edits and bulk paths are unchanged. There is still no default company inferred for imports, restores or historical records. Account `organizationId` is documented as a calendar-bill binding and cannot establish transaction ownership. Existing missing/string ownership, unknown card accounts and reference assignments still need verified treatment.

The current native transaction writer did not enforce a member-role restriction. This slice adds fresh company membership and preserves owner/admin/member/viewer behavior; it does not establish a new viewer policy. CSV import, backup export and restore now require the selected company; bulk/duplicates/receipt-match/search/notification/scheduled-backup authorization remains unsafe (G4). The creation test now asserts that an imported row and an own-company restored row land visibly in the selected company and that other-company/unassigned restore rows are skipped (deliberate flip of the former legacy-unassigned expectations). Generic edits still cannot change this unknown-schema ownership field; that does not make editing another company's row safe.

Company reads from the prior candidate immediately include these newly assigned transactions and exclude them for other companies. No company assignment runs on deployment, old data is preserved, no UI/Navi action is added, and no idempotency key/retry uniqueness or stronger membership/save atomicity guarantee is introduced. Card and historical assignment, linked reference ownership, other global APIs, support/database/key/runtime custody and independent/deployed verification remain open.

Tests use actual native HTTP, synthetic account registration, owned disposable Mongo and the built app. They check the persisted ObjectId and response, forged company payloads, required fields and card-accounting validation, all current member roles, revocation/inactive company/no-write denials, immediate list/detail/statistics/export behavior, selected-company CSV import and restore, edit compatibility, actual original insert versus a second assignment write, twelve parallel company creates and a clean restart. They preserve foreign/unknown documents. Mutation and failure controls must produce specific behavioral assertions; no setup failure counts as detection. No real bank/provider/model call, customer record, historical migration, production write or business send is involved.
