# Trusted company transaction creation

Native `POST /api/transactions` requires the signed-in session's selected company and current active membership. It passes that ObjectId to `createCompanyTransaction`; request body/query company claims never decide ownership. The existing save flow adds the fixed field to this document with a per-path strict override before its one normal save. No schema-wide ownership field, global strict-mode change or second assignment write is introduced. Validation, zero amount, defaults, reference/timeline hooks and timestamps are retained. This company path uses fixed save-error logs/client messages while preserving the existing 400/500 distinction.

`createTransaction` remains the legacy unassigned entry used by CSV import. Card posting, bank import, recurring generation, restore, edits and bulk paths are unchanged. In particular, there is no default company inferred for imports or historical records. Account `organizationId` is documented as a calendar-bill binding and cannot establish transaction ownership. Existing missing/string ownership, unknown card accounts and reference assignments still need verified treatment.

The current native transaction writer did not enforce a member-role restriction. This slice adds fresh company membership and preserves owner/admin/member/viewer behavior; it does not establish a new viewer policy. Global CRUD/update/delete/import/backup/restore authorization remains unsafe. The compatibility restore test checks only that a supplied company field remains rejected by the unchanged strict schema, not that restore is company-safe. Generic edits still cannot change this unknown-schema ownership field; that does not make editing another company's row safe.

Company reads from the prior candidate immediately include these newly assigned transactions and exclude them for other companies. No company assignment runs on deployment, old data is preserved, no UI/Navi action is added, and no idempotency key/retry uniqueness or stronger membership/save atomicity guarantee is introduced. Card and historical assignment, linked reference ownership, other global APIs, support/database/key/runtime custody and independent/deployed verification remain open.

Tests use actual native HTTP, synthetic account registration, owned disposable Mongo and the built app. They check the persisted ObjectId and response, forged company payloads, required fields and card-accounting validation, all current member roles, revocation/inactive company/no-write denials, immediate list/detail/statistics/export behavior, legacy CSV/restore/edit compatibility, actual original insert versus a second assignment write, twelve parallel company creates and a clean restart. They preserve foreign/unknown documents. Mutation and failure controls must produce specific behavioral assertions; no setup failure counts as detection. No real bank/provider/model call, customer record, historical migration, production write or business send is involved.
