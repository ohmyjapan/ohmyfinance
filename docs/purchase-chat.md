# On-page purchase teaching

A shared assistant can be summoned throughout authenticated OMF pages. It expands as an accordion below the application header on desktop and mobile, reserving space above the page instead of covering its content. The conversation has its own bounded scroll area. The assistant stays open across navigation and restores its open state and selected purchase after a tab reload. The worker on the development machine interprets messages using the installed signed-in Claude CLI. OMF on the hosting machine stores owner-scoped conversation jobs, history and proposals. It does not run inference.

A reply can explain evidence or propose purpose, registered customer and the supplied product wording. It cannot post a ledger entry or assign accounting/tax fields. Only the current message can support proposed field values; older messages provide conversational context. An unresolved or conditional instruction asks for clarification. The user confirms each proposal on the page. Reading, sending and receiving replies do not save draft values.

A purchase reply may request OMF's own purchase research instead of telling the user to look up the company identity, the invoice registration number or 勘定科目・区分・税区分・消費税率 themselves. The request is the same research the form on the research card starts, with the reply's one-sentence instruction. An explanation reply queues it at once, bound to the conversation's recorded draft state; a proposal queues it only after the on-page confirmation, bound to the saved draft revision, so the findings never belong to a pre-confirm draft. A status line under the reply says whether the research started, waits for the confirmation, or could not start and why (no research worker seen, one already running, a draft that changed since the message, the per-purchase limits); the running work and its findings appear in the research card below the conversation. Findings remain proposals that still need on-page confirmation; research never changes a draft by itself. The next reply receives the research state, summary, question, findings and supplier candidate as context, marked stale without findings when the draft or source changed after the research ran. A confirmation interrupted between the draft save and the research start is recovered on the next read, once, bound to the accepted draft revision. A reply cannot start research from general conversation.

Purchase replies receive all mapped fields with their selected reference names, evidence, conflicting alternatives, source labels and remaining required fields. Current draft values remain distinct from the original spreadsheet and from unconfirmed suggestions. A known category label can be explained even when its reference has not been selected. Earlier category counts describe only the spreadsheet 区分, and unclassified history is not a contrary customer decision. Questions stay focused on the current request; an optional unknown item does not block an explanation of a known customer or category. Document presence is reported without sending document contents or product URLs. This additional evidence supports discussion, not new accounting/tax edit permissions.

Confirming with the optional memory checkbox stores a customer/purpose lesson atomically with the draft update, under FinanceDraft.teachingMemory. Scope is the exact normalized merchant, the current account, and purchase date onward. Item names are never generalized. Saved corrections win. Different active classifications remain conflicts; explicit source-pattern decisions keep their existing precedence. A later draft classification correction withdraws the old lesson. The learning notebook links each lesson to its source conversation and supports pause/resume with revision checks.

The conversation is limited to 100 messages of 2000 characters; only the last eight messages and the current purchase's evidence go to the interpreter. A new message supersedes an unconfirmed proposal. Confirmed values remain in the draft. No Slack setup is needed.

## Runtime

Use a dedicated owner/account-scoped token (prefix omft_) created by POST /api/finance-chat/agents with accountIds. DELETE /agents/:id revokes it. The token can only claim chat jobs, heartbeat and return validated proposals. It cannot read collector secrets, act as a logged-in user or confirm draft changes.

Store {enabled:true,baseUrl,token,cliPath,inferenceDirectory} with collector/vault.mjs under %USERPROFILE%/.ohmyfinance-teaching (Windows DPAPI), or set OMF_TEACHING_DATA_DIR. Use an empty inference directory outside repositories. Optional claudeConfigDirectory selects an existing signed-in CLI configuration. Optional `nativeOAuthToken` (a long-lived native CLI setup-token, separate from the OMF `token`) is given only to the native CLI child of chat and document interpretation, never to the actions MCP child, a job file or the input; an invalid value stops the reply instead of falling back to another login. Provision or clear it only with `scripts/configure-native-cli-token.mjs` (credential on standard input); see [native CLI credential](native-cli-auth.md). Run committed code: node teaching-worker/run.mjs under a dedicated PM2 process on the development machine. --once handles one poll. No API key is introduced. Tools, MCP servers, settings sources and hooks are disabled; prompts use JSON stdin, the child has a minimal environment, and session persistence is disabled. The CLI exits after each bounded request.

Company public research is the one exception to the no-built-in-tools rule, and it applies only to company conversation jobs. When the claiming worker reports an actual capability, the company interpreter gets the built-in WebSearch, its owned public reader tools in the same actions MCP server, 40 tool turns and a 480-second bound. See [company public research](navi-public-research.md).

The worker reports the capability with each workspace claim; `publicResearch:false` in the teaching Vault turns it off. An optional `ntaApplicationId` in the same Vault enables official registry checks. The id stays in the Vault: it is never in a job file, capture, URL, reply or report.

Purchase and general workspace chats keep `--tools ''`, no public reader, 16 turns and their existing bounds. The separate purchase research worker keeps its private mail/sheet/Issey tools, its own token and its existing Chrome reader defaults. Company public research exposes none of those private tools.

The official [programmatic CLI documentation](https://code.claude.com/docs/en/headless) describes structured output; the [CLI reference](https://code.claude.com/docs/en/cli-reference) defines the isolation flags. This integration retains the existing subscription login rather than bare mode, which does not read subscription credentials.

Claim leases last 120 seconds. During interpretation the worker heartbeats every 20 seconds with the exact job, mode and lease, renewing only its own unexpired working job and unfinished action records. Idle heartbeats report connection status without renewing jobs. Expired, completed or replaced jobs cannot be revived. The interpreter timeout is 240 seconds with action tools and 90 seconds without them. One automatic lease recovery is allowed after interruption, then the user can retry. Worker errors do not log message bodies or credentials. User send IDs are idempotent. Confirmation uses the source hash/key, draft revision, original values fingerprint and an account lease. A saved confirmation is recovered from draft history if the response is interrupted. A later draft edit makes the old proposal stale. The draft and its reusable lesson are one database write, without requiring replica-set transactions.

Action receipts continue to come from the durable journal after a final reply and on earlier turns. Expired unfinished actions are reconciled from their domain markers after a 20-second grace period, without repeating their effects; a live renewed job keeps its in-flight actions protected. Later conversation context and action-status reads use those current receipts. Learning shows active and paused accounting memories even without an imported workbook, including their fields, registered names, card, merchant, purpose/customer, effective date and source instruction. Its revision-checked pause/resume changes future suggestions, not saved drafts or ledger entries.

Chat readiness uses `FinanceChatAgent.chatLastSeenAt`, refreshed only by existing finance-chat claim/workspace-claim/heartbeat endpoints. The 65-second freshness window, owner/account scope, enabled state and revocation checks remain. Research/evaluation/document authentication still refreshes the generic `lastSeenAt` for their existing consumers, but does not make chat appear connected. Existing teaching workers need no new configuration: their normal polls establish the chat heartbeat immediately after the server upgrade. Queued requests remain saved while disconnected; the UI explains that they resume when the connection returns. Failed requests retain the existing retry action and message ID.

The research runtime also composes the existing TeachingWorker with its existing account-scoped token and CLI configuration, with document handling disabled. Each cycle answers at most one chat before polling research/evaluation, so configured cards such as Aplus have a real chat consumer without expanding the separate document worker's account access or granting workspace access. Research polling continues in the same cycle even after a chat reply. During a long research job the composed consumer keeps its chat heartbeat alive every 20 seconds, so users can queue a message while it is busy. The timer is cleared when the job finishes or fails. No account, token or workspace capability is automatically added.

## App-wide assistant

The OMFに相談 button opens general conversation on the current page, or purchase conversation on a draft. Mapping rows also open purchase conversation without navigating. A selected purchase remains pinned when navigating, with its merchant, card and date visible. Switching to another purchase requires the current-purchase action or a row action. General conversation follows page context automatically and includes the selected learning pattern or mapping statement when available. The panel shows which context will be used, and every general message records its page/selection. Existing purchase history and explicit confirmation are preserved. Unsaved draft edits block purchase changes; a late confirmation cannot replace local edits. The panel hides on screen lock and clears in-memory state on logout or user change.

FinanceAssistant stores one general conversation per owner (up to200messages,2000characters each). Only the last8turns enter inference context. General replies cannot contain a purchase patch, and there is no general confirmation endpoint. Server-built context includes the owner's configured accounts, learning summary and up to30active instructions, plus a verified selected pattern with up to8source examples or a selected statement summary. It does not read arbitrary URLs or scrape the DOM; it does not include live ledger totals, credentials or OTP details. Generic page questions work without selecting a purchase. Financial edits and remembered lessons use the existing source-bound purchase conversation.

General conversation requires explicit workspaceEnabled on the owner's FinanceChatAgent. New agents can request it with the authenticated creation endpoint; existing agents are not upgraded implicitly. The worker polls workspace-claim and regular claim separately; only the assigned enabled worker can return a general reply. General chat state is stored separately, so existing purchase conversation IDs and unique indexes do not change. UI session storage holds only open state and selected source identifiers, scoped by user; conversation content remains on the server, and unsent text stays in memory.

## Ledger posting destination

`post_selected_approved_rows` posts to the company the owner's access token selected when the message was sent. The finance-chat route checks that company against a current, active membership; the purchase-chat or workspace turn freezes the actor, company and display name. A request body, a model argument, the card's calendar `organizationId` and later navigation never name or change it. A reused request id returns the original turn and does not take a new company. The purchase chat shows the checked destination below the conversation, marked as used for ledger posting only.

The write uses the same native `commitCompanyImport` path as the company commit route, with its immutable statement/source company intent. Before writing, membership is read fresh (removed or inactive: refused). A statement recorded for another company or source is refused. A row with a reservation or posting not proven for this company is refused and never reported as existing. A row counts as posted or existing only when the statement intent, the `FinanceEntry` reservation and the ledger transaction all name the frozen company. Each posting operation stores the frozen company and its lines from its claim. Recovery after a lost reply checks those fields and the current membership; it writes nothing. A changed ledger, a revoked membership or an operation claimed before these fields existed stays unresolved for the owner. Old operations and unassigned historical rows are not given a company.

Without a selected company (or with a stale or foreign selection, whose name is never returned) the conversation, draft saves, memories, research and approval remain available. Only ledger posting is refused, with an explanation to select a company and send a new instruction.

## Owner and purchase continuation

New chat and history. The owner workspace conversation (200 turns) and each purchase conversation (100 turns) keep their unique identity and a current `segment`. `POST /api/finance-chat/workspace/new` and `POST /api/finance-chat/imports/:importId/drafts/:line/new` (with `chatRevision` and a `requestId`) copy the current segment into `FinanceOwnerConversationArchive` and then empty the live turns in one revision-checked write. The copy includes every journal receipt (done, failed, unresolved), the frozen posting company and the company tag. Concurrent resets of one revision share one copy. A stale un-adopted copy is replaced in place keeping its id (the cb49 rule); nothing is deleted or recreated. A lost reset reply is recognised by its request id. A reset is refused while an answer is being prepared or a receipt is still working. Only the chat resets: drafts, approvals, research, memories, teachings and ledger rows are untouched. An archived proposal is a record; it can never be confirmed or sent as a reference again. `GET .../history` and `GET .../history/:id` are owner-scoped (and draft-ownership-checked for a purchase), list only adopted segments and are read-only. The cap message now points to the new chat instead of a dead end. In the general conversation the owner may choose an archive to discuss. The server then supplies a bounded copy as `discussedArchive`, marked as evidence that is never an instruction or approval. The UI hides the composer while inspecting history.

Owner reply and navigation. A general (workspace) reply may be up to 4000 characters and may carry one `navigation {feature}` from the fixed catalogue. A record id, a query, a URL or an unsupported feature is refused, and the link opens only when the user clicks it. The purchase proposal schema, exact quotes, research and approval rules are unchanged (800 characters, no navigation). `list_navi_features` (both owner realms) reports a feature as `navi_tool` only for tools the current job carries; company-conversation features are page handoffs from here.

Same-company teachings: see [company workspace](navi-company-workspace.md). In short: frozen turn company + workspace worker + fresh membership. Tagged turns stay inside that company in model input, UI and archives. Narrow, companyless, switched or revoked continuations get no company data, and the card discussion is never blocked.

Owner native actions (general conversation, assigned card accounts only; every write on an explicit current instruction, journaled, with its marker in the same native write):
- `get_card_sync_status`: collector paired, job state and times, Aplus schedule. No OTP addresses, tokens or raw errors.
- `queue_card_sync`: the native `queueSync` (same collector/active/busy checks as the page button). `jobOperation` {operationId, jobId} is written in the same enqueue. The receipt says queued, never downloaded.
- `set_card_auto_sync`: the shared `saveAutoSync` helper, now also used by the native settings route. Aplus only, hour 0-23, dotted paths so `lastQueuedDay` is kept, `autoSyncOperation` marker.
- `get_workflow_status`: rows filtered to the assigned cards in the query before counts. No global settings, nightly runs or workers. Step fields are bounded and no file paths are returned.
- `review_workflow_step`: native retry/snooze only, with the row revision. The event carries {operationId, revision}. A saved review is not completed inventory or documents. Note/accept-purchase/documents stay on the page.
- `confirm_card_allocation`, `release_card_allocation`, `reconfirm_card_allocation`: the native allocation writers with the assigned-card read scope applied to the same context before payments, totals and candidates are derived, and to the returned view. The request id is `navi_<operationId>`; release/reconfirm history entries carry the operation. Amount, direction, over-allocation, revision and correction checks are unchanged. The owner page keeps its unrestricted native authority.

Recovery: a lost reply reads that native marker (account, workflow event, allocation request/history, teaching row after a fresh membership check). With a marker the receipt is done/queued; without one it is failed-before-write. Nothing is repeated blindly. Open native pages refresh only the record a Navi receipt names (connections, payments, purchase workflow). The owner panel's ledger destination label is the server-checked company, not the cached organization list. A response requested under one company selection is dropped when the selection changed.

Handoffs that stay interactive: bank CSV import and bank allocations, credentials/OTP/collector pairing and signing, purchase acceptance and document creation, budgets/recurring (C2), normal company adapters (C3), public company research (B). Proof is synthetic owned native HTTP/worker evidence plus installed Chrome (`scripts/finance-navi-owner-continuation-integration.cjs`, `-browser.cjs`, fixture `omf-navi-owner-continuation`). Live-model acceptance, production observation, independent review and deployed replay remain open. This phase does not make the full agent deploy-ready.
