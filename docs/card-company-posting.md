# Explicit company card posting

`POST /api/finance/imports/:id/company-commit` requires the authenticated source owner and fresh active membership of the session's selected company. Body company IDs and account calendar bindings do not select ledger ownership. This is a new explicit API; existing web pages and Navi still use the legacy posting entry and need a later integration change.

The complete decision request is validated before a durable `FinanceImportCompany` intent is claimed. It freezes the owner, account, import, original source hash and selected company. Each new FinanceEntry captures `postingOrganizationId` before ledger insertion. A strict Transaction document validates/casts the ledger payload, then adds only the trusted company field with a per-path override. A single native upsert matches the transaction ID, company and FinanceEntry identity; a conflicting existing row is never rewritten. Transaction schema strictness remains unchanged for legacy writers.

Same-company retries reuse the original intent/reservation and transaction identity. Another selected company, a changed source hash, conflicting reservation or legacy posting attempt on a bound source returns 409. Reservations predating the company intent require separate ownership review; no historical assignment is inferred. Skip-only requests create no company intent. Account leases retain their existing duration and expiry behavior; binding, reservation and ledger writes are separate durable stages, not a cross-collection transaction or a stronger lease/membership atomicity guarantee.

Historical transaction candidates used by this new posting lane require explicit company ownership. Own assigned links preserve existing accounting data; foreign/unassigned candidates cannot link or prevent a valid new posting. The normal owner-scoped review/mapping readers still have global candidate/reference gaps. Legacy unbound posting remains unchanged and unassigned; its compatibility control is not a tenant-safety certification. Global backup/restore/CRUD, reference assignments, source-company UI/Navi, operator/database/key/runtime privacy and production validation remain open.

Tests use the actual built HTTP server with native synthetic registration, account creation and CSV upload in an owned disposable Mongo process. They cover owner/membership checks, request validation, source/company/reservation conflicts, skip/link/new paths, original company insertion, identical purchases, competing company calls, legitimate current member roles and clean restart. Compiled test copies deliberately crash before/after ledger insertion, restart against the same owned database and expire the lease in test data to exercise recovery without waiting a minute. Other test copies reintroduce meaningful defects or query failures; production code contains no crash switch. No live bank, model/provider call, customer record or production assignment is involved.

Independent guard review, historical inputs, an explicit production observation window, UI/Navi integration and the final deployed replay remain required. Assertion/mutant counts are not a reliability percentage.
